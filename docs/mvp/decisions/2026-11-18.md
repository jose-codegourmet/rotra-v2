### D-2026-11-18-01 — Google sign-in ships behind a feature flag that starts off
- **Decision status:** approved (owner, November 18, 2026); the open items below are not decided.
- **Implementation status:** in progress: the flag is seeded off (mock fixture and migration `20261118000100_seed_player_google_sign_in_flag`) and the Player app can read it (#938); no Google screen consumes it yet.
- **Ticket:** [#938](https://github.com/jose-codegourmet/rotra-v2/issues/938) (Epic P12, [#892](https://github.com/jose-codegourmet/rotra-v2/issues/892))
- **Roadmap:** MVP — [Player](../workstreams/player.md), [Admin](../workstreams/admin.md)
- **Decision:**
  - Everything in [D-2026-11-16-01](2026-11-16.md#d-2026-11-16-01) (Epic P12) is gated by one platform feature flag in Admin › Settings › Feature flags: key **`player_google_sign_in`**, name **Google sign-in for players**.
  - **The flag starts off.** It ships already in the catalog, in mock mode and in real mode, so the platform owner does not add it by hand. The platform owner turns it on in Admin (D-FLAG confirmation, Record of actions), with no deploy.
  - **While it is off, the Player app works as it does today:** email + password sign-in and registration, no **Continue with Google**, no Connect Google steps, no ROTRA announcement band, no Sign-in methods card, and the deadline gate never runs.
  - **While it is off, there is no account verification either** (owner report, November 20, 2026: the pinned “Verify your ROTRA account” notification, the “Not verified” chip and the Verification page showed with the flag off). Two of its three steps ([D-2026-11-16-02](2026-11-16.md#d-2026-11-16-02)) need Google, so the reminder, the chip, the Verification buttons and the page all wait for the flag; opening `/profile/verification` goes to the player's profile.
  - **While it is on,** D-2026-11-16-01 applies in full.
  - It is the first flag the apps' code checks, and the first flag that ships with the product. The catalog therefore no longer starts empty: it starts with the flags ROTRA's own features ship with, and the platform owner still adds any other flag with **Add flag**.
- **Open:**
  - Whether the invite card (P-INVITE) and the signed-in join steps (P-JOIN-CLUB, P-JOIN-SESSION) also wait for the flag, or show while it is off with the email + password registration behind them. Until answered: they wait for the flag.
  - Turning the flag off again after players registered with Google only: they have no password. Until answered: a connected Google account keeps working when the flag is off; only new Google registration and the prompts are hidden.
- **Settled (owner, November 18, 2026):** a flag that ships with the product has no "added by" (`created_by_admin_id` and `updated_by_admin_id` are nullable; the migration inserts the row only if it is missing, so an existing value is never overwritten). In real mode the Player app reads the flag server-side over `packages/db` (`@rotra/db/player/feature-flags`), uncached, so it is always fresh; it moves to the Go API with B-04. A missing flag or a failed read is off. Mock mode: off, unless `NEXT_PUBLIC_ROTRA_MOCK_FLAGS=player_google_sign_in` (dev only) forces it on, because Admin's and the Player app's mock stores are separate.
- **Amends:** [D-2026-11-16-01](2026-11-16.md#d-2026-11-16-01) (ships behind the flag); the October 27, 2026 rule "the feature flag catalog starts empty" ([configuration module](../../business_logic/product/admin/modules/configuration/README.md)).

  - Changing the mode after Start (mockup: fixed after Start), and a different mode for one match.
  - A club default in Club settings (mockup: none; every session starts on 16/31).
  - Whether scores stay optional in every mode (mockup: optional), and a best of 3 with game winners but no scores (mockup: stored as the winner only).
  - Whether game scores show on share images and the Facebook post (mockup: no).
  - Whether the mode changes the expected match length (courts and time) or the minimum games estimate (mockup: no).
  - In a deuce mode a normal finish uses the short losing-score entry with Went to deuce for the rest (mockup: yes).
  - Database: whether the game rows also go into the frozen result evidence and the finalized facts; how old data reads (proposed: 16/31).
- **Amended November 19, 2026 (picker only):** the setup picker shows the game points first (31 points, 21 points, 21 × 3) and then a **Deuce** switch, on illustrated cards (owner: “picking the game points first and then a switch to include Deuce or not”; [log](../../mockup-changes/2026-11-19-queue-mode-scoring-cards.md)). ### D-2026-11-18-07 — A guest's invite link claims that guest's record
- **Decision status:** approved (owner, November 18, 2026: “As a QM, I created an Account for them, that guest account was intended for them until they feel ready to use that account. So if they enter their details. and they register. That ACCOUNT WAS FOR THEM”). The open items are not decided.
- **Implementation status:** mockup, mock app and real mode written in one change ([log](../../mockup-changes/2026-11-18-queue-guest-invite-claims-record.md)); not run in a browser or against a database yet. No migration: `club_player_claim_links` already exists.
- **Ticket:** [#966](https://github.com/jose-codegourmet/rotra-v2/issues/966) (epic Q24)
- **Roadmap:** MVP — [Queue](../workstreams/queue.md), [Player](../workstreams/player.md)
- **Problem it fixes:** a guest's **Copy invite link** copied the generic club invite link, so a guest who registered got a second club player record and their own record, games and session slots stayed behind.
- **Decision:**
  - **The invite link made from a guest's own profile belongs to that guest.** Invite to ROTRA › **Copy invite link** and **Share** on the guest's profile, and **Invite** in Saved players, make that guest's own registration link (`/claim/<token>`), the kind an unclaimed player already gets: it works once, lasts 7 days, and a new link cancels the earlier one.
  - **Registering through it claims that club player record.** The name and nickname prefill the form; the person types their own email and phone and sets a password (or uses Google). The new account is attached to that same record, so their games and session slots stay with them. No second record is made. They get their RTR ID then, from the inviting club's place, as any club record does.
  - **The link is the proof.** Nobody is matched or merged by name alone.
  - **Every existing guard stays:** an email that already has an account or a login is refused, a phone that belongs to another profile is refused, and an expired, used or replaced link doesn't work. A person who already has an account cannot attach a guest record through the link; nothing is merged.
  - **Unchanged:** the generic club invite link (Club settings, the invite card and its QR) and guest join requests on the public session page.
- **Open:**
  - A returning guest's new join request on the public session page still makes a second guest record.
  - A guest who registers through the generic club link or the session page's register link, instead of their own link, still starts a new record. The Queue Master's **Same person** move remains the remedy for both.
  - A person who already has a ROTRA account and played as a guest: their own link refuses their email and phone (mockup and app: no merge).
  - History attribution for the claimed record's earlier games (one attribution per joined record) stays open, as in [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04).
- **Amends:** [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04) (“A guest's games never join an account by themselves. They come along only after the club makes the guest unclaimed by adding an email.”) and the guest invitation note of November 8, 2026 (#490: “Registration keeps the guest record unlinked”) for a guest's own link.
