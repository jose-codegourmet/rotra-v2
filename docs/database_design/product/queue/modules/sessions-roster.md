Set when the club saves the person with an email: an unclaimed record must have one, and other clubs' records for the same email point to the same entry (same RTR ID). Kept after registration, when `player_id` is set too. A row with no email and no link is a guest; a row with a private phone and no entry is an older record that reads as **Details required**. No new column. Adding a registered player no longer copies their nickname here, and registration clears it on the joined rows. | `saved_skill_level_id`, `saved_level_at` | **Built 2026-11-23 (migration `20261123000300_club_player_saved_level`, applied to the shared database).** Nullable `SMALLINT` → `skill_levels(id)` and its time (CHECK: both or neither). The level the club gives a saved player outside a session (Saved players › Add player, Edit details). Session levels stay in `club_assessments`; Saved players show whichever of the two is newer |
| `removed_at` | Nullable timestamptz: the club deleted this saved player (November 8, 2026). Soft delete, because history (`session_players`, facts, summaries, assessments) keeps pointing at the row. Removed rows are left out of Saved players, its counts, search and Add player; adding the same linked profile again clears it. **Leave club and rejoin (#1018, [D-2026-11-22-07](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-07)):** a player leaving sets this on their own row and, in the same transaction, moves every pending `session_slot_transfers` row of theirs in this club (sender or recipient) to `cancelled`; rejoining (club or session link, transfer-link claim) clears it on the same row, so (club_id, player_id) never has a second row. A player's own leave and a club's deletion are not told apart (no extra column; no migration). Leaving also ends the player's current `club_trusted_hosts` row in this club (below), and rejoining writes none |
| `created_at`, `updated_at`, `revision` | Common metadata |

Unique `(club_id, id)` supports scoped FKs. Unique `(club_id, player_id)` and `(club_id, shared_entry_id)` (NULLs never collide) prevent duplicate canonical members of the saved list. Name is **not unique**. Index `(club_id, display_name, id)` for saved-list lookup; substring/fuzzy indexing is a later query-driven choice.

A guest can persist here indefinitely without a global profile. A guest's games never join an account by name or by themselves ([D-2026-11-16-04](../../../../mvp/decisions/2026-11-16.md#d-2026-11-16-04)). After the guest registers through their own invite link ([D-2026-11-18-07](../../../../mvp/decisions/2026-11-18.md#d-2026-11-18-07): a `club_player_claim_links` row for a record with no email, phone or shared entry; registration sets `club_players.player_id` on that same row, no new table or column), or after the club adds the guest's email and the person registers (before November 16, 2026: after confirmed identity linkage), earlier valid games must be included in personal history and ranking under existing eligibility/window rules (owner decision, October 28, 2026). Preserve historical identity snapshots and permanent results; use an auditable, repeat-safe attribution/projection mechanism rather than blindly rewriting old facts. Confirmation evidence and duplicate/mistaken-link resolution remain open.

`club_player_private_inputs`: optional one-to-one private intake for operator-entered normalized phone, email, and preset identity fields (since P15.8, [D-2026-11-16-04](../../../../mvp/decisions/2026-11-16.md#d-2026-11-16-04): the email of an unclaimed record lives on its shared entry, not here, and the club cannot update it once set; the phone is optional and never the key; `preset_fields` holds the club's own playing style, experience and links for its unclaimed record, versioned JSON, no new column), with capture timestamps and resolution state. Do not duplicate already-known hidden contacts. On successful resolution, minimize/purge redundant intake according to a policy still to be decided. Pending contact fields never appear in public roster payloads.

Duplicate offline entries can conflict on linking. Quarantine the link operation and retain both source IDs until reviewed; do not merge by name or rewrite confirmed match participants automatically.

## `club_trusted_hosts`

**Built (#1003, migration `20261122000100_club_trusted_hosts`; written and applied to a local disposable database only).** A club's trusted-host list, drawn from its saved players ([D-2026-11-22-01](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-01)). Informational only: no role, permission or sign-in reads it, and the club account stays the only way to operate the Queue app. Prisma: `ClubTrustedHost` in `schema/queue/club-host.prisma`.

| Field | Type / rule |
|---|---|
| `id` | UUID PK |
| `club_id` | UUID FK to clubs; required |
| `club_player_id` | UUID; scoped FK `(club_id, club_player_id)` → `club_players(club_id, id)`, ON DELETE RESTRICT. Any saved player: registered, unclaimed or guest (no ROTRA account needed) |
| `added_at` | Timestamptz the club put them on the list |
| `removed_at` | Nullable timestamptz: the club took them off, or the player left the club (#1018, [D-2026-11-22-07](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-07): `leaveMyClub` ends the current row on the record left and on records moved into it, in the same transaction; rejoining never restores it). Null = currently trusted. Soft, so the saved player, past rows and later session host records stay; adding them again makes a new row. CHECK: not before `added_at` |
| `created_at`, `updated_at`, `revision` | Common metadata |

Partial unique index `club_trusted_hosts_one_current` on `(club_id, club_player_id) WHERE removed_at IS NULL`: one current row per saved player. Index `(club_id, club_player_id)`, unique `(club_id, id)`. RLS on, no anon/authenticated grants. Reads leave out a saved player the club deleted or moved into another (Same person); the row stays as history. Session hosts are in [`session_hosts`](#session_hosts) below, with the snapshots that keep finished sessions' hosts (#1008).

## `session_hosts`

**Built (#1004, migration `20261122000200_session_hosts`; written and applied to a local disposable database only).** A Queue Session's hosts: saved players of the club assigned to host that session ([D-2026-11-22-01](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-01)). Shown, never a permission. Prisma: `SessionHost` in `schema/queue/club-host.prisma`.

| Field | Type / rule |
|---|---|
| `id` | UUID PK |
| `club_id` | UUID FK to clubs; required |
| `session_id` | UUID; scoped FK `(club_id, session_id)` → `queue_sessions(club_id, id)`, ON DELETE RESTRICT (deleting a prepared session deletes its host rows first) |
| `club_player_id` | UUID; scoped FK `(club_id, club_player_id)` → `club_players(club_id, id)`, ON DELETE RESTRICT. Any saved player; a new host must be a current trusted host when assigned (service rule) |
| `assigned_at` | Timestamptz the saved player became a host of the session |
| `removed_at` | Nullable timestamptz: the host designation ended. Null = current host. Never touches their `session_players` / `session_waitlist` row. CHECK: not before `assigned_at` |
| `name_snapshot` | Text, required, not blank (#1008): the host's name at assignment (the ROTRA full name for a linked record, else `club_players.display_name`); refreshed once more when the session ends (unless the saved player was already deleted or moved) |
| `frozen_at` | Nullable timestamptz (#1008): set when the session ended (Session done or Mark session invalid) on the rows current then; those rows are the finished session's hosts. CHECK: only with `removed_at` null. Trigger `session_hosts_frozen_guard`: a frozen row is never changed or deleted, and `frozen_at` is set only on a completed or invalid session |
| `created_at`, `updated_at`, `revision` | Common metadata |

Partial unique index `session_hosts_one_current` on `(session_id, club_player_id) WHERE removed_at IS NULL`: one current row per saved player and session. Indexes `(club_id, session_id)`, `(club_id, club_player_id)`, unique `(club_id, id)`. RLS on, no anon/authenticated grants.

**Read by the public page (#1006).** `readPublicSession` and the Player app's access read select the session's current rows (`removed_at IS NULL`, oldest `assigned_at` first) in the same transaction as the roster, and join the saved player for name, picture and level through the same masking as roster entries (the roster entry's name snapshot wins; a host with no roster entry uses the saved player's name and latest assessment). Only the masked or signed-in-allowed projection leaves the server: no ids, no club nickname. No schema change.

**Written with the roster.** The create and Edit preparation saves (`hostClubPlayerIds`) write host rows in the same transaction as their roster entries: a new host who holds no live slot and no waitlist place gets a `session_players` row while one is open (their latest club assessment selected, or none), otherwise a `session_waitlist` row at the end (the preparation rule). A released entry is reactivated rather than duplicated (unique `(session_id, club_player_id)`). Ending a host row leaves the registration. Each new row gets its `name_snapshot`.

**Changed during a session (#1005, no schema change).** `POST /api/sessions/{id}/hosts` (one `clubPlayerId`) and `DELETE /api/sessions/{id}/hosts/{clubPlayerId}` run on the locked session, before or during play, and bump the session revision. Add creates the host row with the same placement as above (`placeClubMember` when a club assessment exists; in a live session a host with no assessment and no registration is refused). Remove sets `removed_at` and nothing else: no write to `session_players`, `session_waitlist`, `club_trusted_hosts`. No roster, withdrawal or sit-out path writes `session_hosts`, so withdrawing keeps the current row.

**Finished sessions keep their hosts (#1008, migration `20261122000300_session_host_snapshots`; applied to a local disposable database only).** `finalizeSession` (after `state = completed`) and `invalidateSession` (after `state = invalid`) run `freezeSessionHostsIn` in their transaction: every row with `removed_at` and `frozen_at` null gets the saved player's current name (kept as it was for a deleted or moved record) and `frozen_at`. Reads choose rows by `shownHostRows(state)`: prepared and active sessions `removed_at IS NULL`; completed and invalid sessions `frozen_at IS NOT NULL`, named by `name_snapshot` (the public read masks it as before). So trusted-host removal (`club_trusted_hosts.removed_at`), saved-player deletion (`club_players.removed_at`) and Same person (`linked_to_club_player_id`, the row keeps its `club_player_id`) leave finished sessions unchanged. Same person during an open session repoints that session's current host row to the surviving record with its name, or ends it when that record already hosts the session. No `player_id` snapshot: the RESTRICT FK keeps the record, and its picture, reachable. Backfill: `name_snapshot` from the saved player; current rows of completed or invalid sessions frozen at `finalized_at` (else `updated_at`).

|---|---|
| `bagging_on` on `queue_sessions` | Boolean, default false. Meaningful only when `allow_doubles` is true (the switch is not offered otherwise). Off keeps the pairs; Generate ignores them |

Generate matches reads the pairs when it drafts doubles (the lower of the two players' adjusted games played plus 1 is the pair's next game number); a pair is a guide and creates no match, result or credit. Auto Queue (court filling) and hand-built matches never read it.

Proposed unique `(club_id, id)` and partial unique `(club_id)` for state in active/finalizing. This protects server-known active state but cannot alone prevent two disconnected sessions from starting.

**Additional proposal:** `club_session_reservations` has `club_id` as PK, unique `session_id`, and a scoped FK to the session. Acquire it online before issuing permission to start that session offline. Different devices may operate the same reserved session for recovery. Downloading a read-only/preparation copy need not acquire a reservation; the exact activation UX is open. No second distinct session receives offline-start permission while the reservation exists.

> MVP: offline start is out of MVP under [D-2026-11-07-03](../../../../mvp/decisions/2026-11-07.md#d-2026-11-07-03), so this reservation is moot for MVP.

**No overlapping sessions.** A club's non-invalid, non-cancelled sessions must not overlap in time. Enforce it with an exclusion constraint, `EXCLUDE USING gist (club_id WITH =, tstzrange(scheduled_start_at, scheduled_end_at) WITH &&) WHERE (state IN ('prepared', 'active', 'finalizing', 'completed'))` (needs `btree_gist`; drafted in `20261106000100`, listing the counted states because a new enum value can't be used in the migration that adds it), plus a command-level check that reports which session clashes and whether it is the same venue (venue clash) or another venue (time clash). Creating a series inserts only the free dates, in one transaction. Extending a running session's end time must pass the same check.

Session timestamps from a device are evidence, not automatic proof of an unexpired license. Offline start/expiry rules need a trusted authorization design.

## `session_waitlist`

**Stepping down (owner decisions, November 11, 2026, #735; [log](../../../../mockup-changes/2026-11-11-queue-roster-waitlist-overfill.md)).** **Move to waitlist** (Queue Master, or the signed-in player for themselves) deletes the player's `session_players` row and inserts a `session_waitlist` row at the **front** of the order, carrying their `skill_level_id`; the paid mark stays on the session's payment marks and shows again if they regain a slot ([D-2026-11-11-06](../../../../mvp/decisions/2026-11-11.md#d-2026-11-11-06)). It is allowed before Start and after Start, **refused when the player is in any waiting, On court or Playing match** (server-side check), in one transaction like **Give slot**. This is a demotion, so it does not conflict with “roster removal only while prepared” below. Front placement uses the same ordering contract as the budget rule below ([#245](https://github.com/jose-codegourmet/rotra-v2/issues/245)); no new position field is approved here. Overfilling (Add anyway, Give slot anyway) stores nothing new beyond the existing `over_budget_at` marker; the 25/24 count and expected games are derived. Open: whether finished games of a stepped-down player stay in tonight's standings (the record keeps them).

**Self check-in marks (owner go-ahead November 18, 2026, [D-2026-11-09-03](../../../../mvp/decisions/2026-11-09.md#d-2026-11-09-03); migration `20261118000600_self_check_in`, written November 18, 2026; applied to a local disposable database 2026-11-19; **applied to the shared database 2026-11-19** (`prisma db execute` + `migrate resolve`; `20261114000400_sign_in_tables` held then, applied to the shared database 2026-11-23)).** Two nullable timestamps on `session_players`: `self_checked_in_at` (the signed-in Player's own **I'm here**) and `left_at` (**I'm leaving**), each written together with `present` and `present_changed_at`. The roster shows “checked in themselves” only while present and `present_changed_at` is not later than `self_checked_in_at`, and “Left” only while not present and `present_changed_at` is not later than `left_at`, so any later presence change by the Queue Master hides the mark without clearing the column. Neither column is level-locked.

**No show (cancelled) (owner comment, November 13, 2026; decided November 14, 2026, #839, [D-2026-11-14-02](../../../../mvp/decisions/2026-11-14.md#d-2026-11-14-02); migration `20261114000300_session_players_no_show`; [log](../../../../mockup-changes/2026-11-13-queue-no-show-cancelled.md)).** A nullable `no_show_at timestamptz(6)` on `session_players` marks the entry instead of releasing or deleting it (a no show is only possible after Start, when the level is locked and the level-lock trigger forbids a release). A hand-written CHECK `session_players_no_show_check` (`no_show_at IS NULL OR released_at IS NULL`) keeps release and no show apart; the level-lock trigger is unchanged. **The live roster is `released_at IS NULL AND no_show_at IS NULL`** everywhere: slot counts and capacity, Start, auto-pairing and match rules, presence and match requests, standings and results, finalization facts and summaries, Payments and the fee split, the public session page and the player's own sessions. **Back to roster** clears `no_show_at` (refused while the live roster is at capacity) and keeps the slot order, level and paid mark. Rules: only while the session is `active` (Remove from roster covers prepared sessions); the entry is live, not present, has no games (counted plus Set games played adjustment) and no participation in a decided match, and is in no waiting, On court or Playing match (all server-side). Payments: a no show owes nothing: they are off the Payments list and out of the fee split while marked, and their stored paid mark (keyed on the entry) is kept and shows again after **Back to roster** (the same rule as Move to waitlist, [D-2026-11-11-06](../../../../mvp/decisions/2026-11-11.md#d-2026-11-11-06)). Visibility: shown only on the Queue console's live Players view (the **No show (cancelled)** panel, from the roster read's `noShows`); never on the player's own history or the public session page, and out of standings and finalization like any non-participant.

| Field | Type / rule |
|---|---|
| `id`, `club_id`, `session_id`, `club_player_id` | UUID keys with scoped FKs |
| `skill_level_id` | Level chosen when added; becomes the roster level when given a slot |
| `added_at` | Historical arrival/entry time; insufficient by itself to encode all waitlist priority |

Unique `(session_id, club_player_id)`, and a player can't be both waitlisted and on the roster for the same session (command check). **Give slot** deletes the waitlist row and inserts the `session_players` row in one transaction, recording when it went over budget. Slot counts are derived, never stored.

**Budget changes in preparation** (first come, first served): when capacity shrinks, move the latest-confirmed roster entries beyond the budget to the **front of the existing waitlist**, preserving their relative joining order, in one transaction. Growing the budget fills from that resulting order. Active sessions are never rebalanced: removing a court there unseats nobody.

Copying `confirmed_at` into `added_at` does not guarantee this rule: an earlier guest request can already be waiting. Preserve historical timestamps and define ordering separately. Equal-time ties, repeated demotion/promotion and concurrent saves need the reviewed durable ordering contract in [#245](https://github.com/jose-codegourmet/rotra-v2/issues/245); no new position field or timestamp-rewriting scheme is approved here.

## `session_slot_transfers`

**Transfer my slot** from a confirmed signed-in Player before start ([D-2026-11-22-03](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-03), #1011, epic #1009). Schema file `packages/db/prisma/schema/queue/slot-transfer.prisma`. Columns: `id`; `club_id`, `session_id` (scoped FK to `queue_sessions`); `sender_session_player_id` (scoped FK `(club_id, session_id, sender_session_player_id)` to `session_players`: the slot being transferred), `sender_club_player_id` (scoped FK to `club_players`), `sender_player_id` (to `players`), frozen at request time; `recipient_player_id` (to `players`; the registered player picked by exact RTR ID; **nullable** only so a transfer link nobody has claimed yet fits, #1012); `recipient_club_player_id`, `recipient_session_player_id` (scoped FKs; set on approval: the recipient's saved player, created when new to the club, and the entry that now holds the slot); `recipient_was_waitlisted` (set on approval); `status` (`slot_transfer_status`: `pending`, `approved`, `rejected`, `withdrawn`, `expired`, `cancelled`); `requested_at`; `decided_at` (any final status); `decided_by_device_id` (scoped FK to `devices`; Approve or Reject on a known device, else null); `withdrawn_by_player_id` (to `players`); `created_at`. No `updated_at` and no revision: a row changes at most once.

- **Concurrency.** Every write locks the session row (`lockSession`, `FOR UPDATE`) and then the transfer row (`FOR UPDATE`), so approvals, Start, Cancel session and the player's own writes on one session run one at a time. Approval is one transaction: release the sender's entry (`released_at`, `release_reason = 'transferred'`, a new value of `roster_release_reason`), find or save the recipient's club player (`clubPlayerForProfile`), give their waitlist row (or a new one) the chosen level and promote it (`promoteWaiter`, which reactivates a released entry of theirs instead of inserting a second), set the recipient entry's `confirmed_at` to the sender's (slot order kept), close the recipient's pending join requests and the sender's open drop-out notice, then mark the transfer `approved`. The live count is unchanged. `session_players (session_id, club_player_id)` and `(session_id, player_id_at_entry)` stay unique, so a duplicate registration is impossible.
- **Constraints (hand-written).** Partial unique index `session_slot_transfers_one_pending_per_entry` (`sender_session_player_id` WHERE `status = 'pending'`). CHECKs: `decided_check` (`pending` exactly when `decided_at` is null); `approved_check` (approved names the recipient player, club player, entry and `recipient_was_waitlisted`); `recipient_set_on_approval_only`; `not_self` (recipient ≠ sender); `device_check` (a device only on `approved` / `rejected`); `withdrawn_check` (`withdrawn_by_player_id` exactly when `withdrawn`). Trigger `session_slot_transfers_final`: UPDATE of a row that is not pending, and every DELETE, raise `restrict_violation` (immutable once decided; the chain of custody is never rewritten). Server-only: RLS on, `REVOKE ALL … FROM anon, authenticated, PUBLIC`.
- **Lifecycle.** Start (`startSession`) sets every pending row `expired`; Cancel session sets them `cancelled`. Finish and invalid never meet a pending row (they come after Start).
- **Payments.** The sender's `session_payment_marks` row stays on the released sender entry, exactly as recorded; no approval writes or changes a mark. Rejection writes nothing else.
- **Payment snapshot (#1013, [D-2026-11-22-05](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-05)).** Five nullable columns written by the same UPDATE that sets `approved`, never after (the row is final): `amount_due_minor` (the amount due per player at approval; null with no fee set), `amount_paid_minor` (cash collected for the slot by every holder so far: the sender's own mark, unless frozen, plus what an earlier approval carried to them), `prior_waived_minor` (waivers of earlier approvals in the chain), `waived_minor` (the automatic waiver: what the slot still owed) and `currency` (`PHP`). Readers (`slotLedger` in `packages/db/src/queue/transfer-accounting.ts`, the same pure rules as the mock in `@rotra/data/slot-transfer/transferAccounting.rules`) give the live holder's entry the last approval's `amount_paid_minor` as carried cash and `prior_waived_minor + waived_minor` as waived, plus any own mark recorded after; senders are off the roster, so cash counts once and collected totals never change. Approve recomputes the snapshot under the session lock and refuses (409) when it differs from the waiver the Queue Master was shown (`expectedWaiverMinor`). Hand-written CHECKs: `payment_on_approval_only` (all null unless approved), `payment_check` (approved rows carry paid, prior waived, waived and currency), `payment_nonnegative`, `waiver_check` (`waived_minor` = `GREATEST(amount_due_minor − amount_paid_minor − prior_waived_minor, 0)`, or 0 with no fee set), `currency_check` (`PHP`). Trigger `session_payment_marks_frozen_by_transfer` on `session_payment_marks`: UPDATE or DELETE of a mark whose entry is the sender of an approved transfer decided at or after the mark's `marked_at` raises `restrict_violation`. The services also lock a transferred-in entry's payment (no tick, untick, amount or Mark all paid). No new table: a waiver is a column of the approval it belongs to, so the chain (original payer, each recipient, amounts, waivers, approval times and device) is the ordered set of approved rows.
- **Reject and refund (#1014, [D-2026-11-22-06](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-06)).** The transfer row reads `rejected`; one [`session_payment_refunds`](financials-inventory.md#session_payment_refunds) row references it (`slot_transfer_id`). The same transaction releases the sender's entry with `release_reason = 'refunded'` (a new value of `roster_release_reason`) and promotes the first waitlist row with a level while a slot is open (FIFO, `orderedWaitlist` + `promoteWaiter`); capacity is unchanged.
- **Room for the later tickets (shape only; nothing built):** `@@unique([club_id, session_id, id])` is the scoped target for rows that belong to one transfer. **#1012 transfer links**: built, see *Transfer links* below (columns on this row, not a separate table). **#1013 accounting**: built, see *Payment snapshot* above; repeat transfers chain through `sender_session_player_id` = the previous approved row's `recipient_session_player_id`, so original payer, recipients, approvals and dates are already recoverable. **#1014 refunds**: a separate append-only refund record referencing this row. **#1018**: leaving a club sets the pending rows it touches to `cancelled`.

- **Transfer links (#1012, [D-2026-11-22-04](../../../../mvp/decisions/2026-11-22.md#d-2026-11-22-04)).** A link is this row, not a separate table: the link and its transfer are one to one and the link works exactly while the row is `pending`, so a separate state would only repeat this one. Two nullable columns: `link_token_digest` (`BYTEA`, unique; SHA-256 of the opaque token, 32 random bytes in base64url, like `player_claim_links.token_digest`; null for a transfer by RTR ID) and `claimed_at` (when the first signed-in claimant took it). A link row starts with `recipient_player_id` null. **Claim**: on the locked session and transfer rows, `UPDATE … SET recipient_player_id = $claimant, claimed_at = now() WHERE id = $id AND status = 'pending' AND recipient_player_id IS NULL`; zero rows means someone else claimed first. **Claimant withdraws**: `withdrawn` with `withdrawn_by_player_id` = the claimant (the recipient stays on the row as a record). **Invalidation**: rejection, either side's withdrawal, Start (`expired`) and Cancel session (`cancelled`) all leave `pending`, and the link with it; a new link is a new row. An unclaimed link is not listed in Requests. Hand-written CHECKs: `link_or_recipient` (a recipient or a link), `claimed_check` (`claimed_at` exactly when a link has a recipient), `rejected_check` (only a transfer with a recipient is rejected), `link_digest_length` (32 bytes). The trigger `session_slot_transfers_final` now also refuses, on a pending row, any change of `link_token_digest`, of a `recipient_player_id` once set, or of `claimed_at` once set (one claimant per link). #1018 adds club membership where the claim service marks it.

**Written November 22, 2026** (migration `20261122000500_slot_transfer_links` for the transfer links, and migration `20261122000400_session_slot_transfers`; applied to a local disposable database 2026-11-22 only; **not applied to the shared database: owner sign-off needed**).

Choosing a venue copies its rate into `session_cost_estimates.court_fee_per_court_hour_minor`; editing the session's fee never updates the venue. Venue deletion is not specified; keep rows referenced by sessions.

## `session_players`

| Field | Type / rule |
|---|---|
| `id`, `club_id`, `session_id`, `club_player_id` | UUID keys with scoped FKs |
| `player_id_at_entry` | Optional global profile FK; no forced profile for guests |
| `name_snapshot` | Display at entry |
| `present` | Operator-controlled boolean; false when added in preparation, true when added to an active session |
| `present_changed_at` | Timestamp of the last presence change (reset to the start time at session start); feeds the derived wait time |

Drives the “checked in themselves” mark; the operator's last action wins |
| `left_at` | Nullable timestamp of the player's own **I'm leaving**; cleared by the next check-in or when the operator sets Present. The QM roster shows “Checked in themselves · TIME” and “Left · TIME” from these two fields |
| `assessment_id` | FK to the roster assessment revision selected for this entry |
| `skill_level_id` | FK to one of the nine levels; required on confirmation/start/late entry. Permitted missing-level preparation states and physical nullability remain unresolved in #245 |
| `level_locked_at` | Null before start; set at start or on late entry |
| `games_adjustment` | Integer, default 0, may be negative (#717, owner decisions November 11, 2026). The Queue Master's **Set games played** override, stored as requested − games counted from completed matches at override time, so displayed games played = counted + adjustment (floored at 0) and keeps counting up. Session-running aid only: facts, results and rank never read it. **Drafted** in migration `20261111000300_roster_games_adjustment`, applied 2026-11-11 |
| `confirmed_at`, `joined_at`, `revision` | Timestamps/revision |

Unique `(session_id, club_player_id)` and partial unique `(session_id, player_id_at_entry)` for known profiles. Composite unique `(club_id, session_id, id)` supports match participation FKs.

The roster/assessment relationship is cyclic: create the roster and assessment in one transaction using a deferred FK or an initially nullable selected-assessment pointer, then validate it before accepting the roster entry. The selected assessment must reference this exact club/player/session entry, not merely any existing assessment UUID.

Lock existing entries' levels on start and late entrants on insertion into the active session. Prevent level/assessment-reference changes after lock. Presence remains editable. `session_players` carries no resting, waitlist, payment, or player self-admission state; the waitlist, paid marks and guest join requests live in their own tables (`session_waitlist`, `session_payment_marks`, `session_join_requests`).

Start is refused while any entry lacks `skill_level_id`. This defensive check does **not** decide column nullability: business rules require a level to confirm a slot, while screen states include missing-level prepared rows. Specify which states may persist before choosing the constraint ([#245](https://github.com/jose-codegourmet/rotra-v2/issues/245)).

Roster removal is allowed only while the session is `prepared`; this does not authorize physically deleting a row referenced by paid marks or already-synced assessments. The removal/demotion identity and retention policy, and whether those assessments still count, remain open in #245. The Give slot delete/insert description above is a proposal subject to that gate. Active sessions cannot remove entries; presence is turned off instead.

Wait time (minutes since the player's last completed/invalid match ended, or since `present_changed_at`) is derived at read time, never stored.

The roster's global link is a historical snapshot. Resolve later identity corrections through explicit linkage history/policy, not hidden retargeting of match facts.

## `session_courts`

| Field | Type / rule |
|---|---|
| `id`, `club_id`, `session_id` | UUID keys |
| `label` | Text; defaults to "Court N" |
| `open_until` | Nullable timestamptz. Null means "until the session ends" and follows `scheduled_end_at` whenever the end changes. A set time must be later than the moment it is added and not after the session end |
| `removed_at` | Nullable; set when a free court is removed |
| `starts_at` | Nullable timestamptz (settled November 6, 2026): the court's planned start; null = the session start. A set `open_until` is after it |
| `opened_early_at` | Nullable timestamptz (settled November 6, 2026; needs a `starts_at`); set by **Start anyway** when the court is opened before its planned start, cleared by **Undo early open** while the court is free. The planned start is never rewritten. Counts as use, so the planned start is fixed while it is set |
| `revision`, timestamps | Common metadata |

Unique `(club_id, session_id, id)`. Unique `(session_id, label)` among non-removed courts (partial index on `removed_at IS NULL`).

Add courts during the session without changing club founding location. **Editing a court is allowed while a match is on it (owner comment, November 11, 2026; [log](../../../../mockup-changes/2026-11-11-queue-courts-and-time-sheet.md)):** `open_until` and the label may change, `starts_at` stays fixed once the court has been used, and the match is untouched; only removal needs a free court. Remove only a court with no active hold, and keep at least one non-removed court; soft-remove because historical `match_court_usage` may reference it. `open_until` is a reminder: no command or constraint ends a match when it passes. "Booking ended" is derived.

Setting the end time updates `scheduled_end_at` (owner decision, November 6, 2026): after start it may move to any instant after now, later or earlier, up to 24 hours after `started_at`; **Extend 30 min / 60 min** are shortcuts for the same update. Reject a new end before a non-removed court's set `open_until` or at/before a court's planned start. Courts with null `open_until` follow it; set ones do not. Keep the change as an ordinary revisioned update or sync operation. A late or other-day Start session may carry a new `scheduled_end_at` in the same transition. `started_at` is fixed once set: it records when play began and no live command edits it.

**Times carry their day (November 6, 2026).** `scheduled_start_at`, `scheduled_end_at`, `open_until` and a court's planned start are full instants (`timestamptz`), never clock-only values with an inferred "next day". The court's planned start is `starts_at` (mock `startsAt`), a nullable timestamptz (null = session start), drafted in `20261106000100`. Display and entry use the club's time zone (Asia/Manila for v1); storage stays instants per the [conventions](../../conventions.md).

## Queue flexibility handoff (October 31, 2026)

The approved product contract uses the prepared slot budget with an explicit override and permits direct active-session admission above it. Court windows have individual planned starts and advisory ends, with starts fixed after use and session-end-following ends distinguished from fixed ends. Reconcile the proposed storage and command validation with these rules in the database epic; this note does not authorize schema or migration changes.

### Court-window actual-start boundary (#320, owner decision November 1, 2026)

For live sessions, new court-window commands validate against `queue_sessions.started_at` rather
than `scheduled_start_at`. At Start session, default court starts follow the actual start;
deliberately staggered starts keep their times. Preserve the scheduled session timestamp and
existing earlier starts on edit; used starts remain fixed. This clarifies command behavior using
existing proposed fields and adds no table, column, or migration.
