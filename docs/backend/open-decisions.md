| B-21 | **WebAssembly toolchain and hosting for the shared rules.** **Tool:** standard Go (`GOOS=js GOARCH=wasm`, the same compiler as the server) if it passes the spike's marks; TinyGo if it doesn't. Either way the rules stay plain Go that both compile, and the tool version is pinned. **Build:** the built `.wasm` is committed to `packages/rules-wasm`; CI rebuilds it and fails if it doesn't match the Go source, so Vercel needs no Go. A merge conflict on the file is fixed by rebuilding. The build records a fingerprint of the Go rule files; `make check` recomputes it in Node and fails on a difference, so the gate needs no Go. `packages/rules-wasm/` is a backend CI path, so a rule change and its rebuilt file merge in one PR. **Hosting:** it ships with the apps as a static file on Vercel (already a CDN), not on S3 or a bucket, so the wrapper and the `.wasm` always deploy together. The file name carries a content hash (`rules.<hash>.wasm`) and is served as immutable, cached like the app's JavaScript, so a device downloads each rules version once (loading after an offline reload waits for a service worker, backlog BL-6). **Size mark** raised from 500 KB to 1.5 MB compressed, since the file is downloaded once per version; the 300 ms load mark on a mid-range phone stays the real test. The spike picks the tool by this rule and returns to the owner only if both tools fail | 2026-11-14 | [D-2026-11-14-01](../mvp/decisions.md#d-2026-11-14-01); [rule-cases spec](../../conductor/tracks/rule-cases_20261113/spec.md#r0-spike-throwaway-not-merged) |
| B-22 | **Shared rules are versioned per Queue Session.** One `rulesVersion` number covers the whole set of shared queue rules (no per-rule versions). Start is online only, so the server stamps the session when it starts, with the highest version that both the Go API and the live apps' `rules-manifest.json` carry (cached about a minute; if unreadable, the last confirmed version, never guessing upward; `RULES_VERSION_MAX` in Railway caps it, normally unset, and the server refuses to start if the cap names a version it doesn't have). No manual switch and no maintenance mode; the device stores it with its offline copy. The device runs every offline command under the session's version and the server replays it under the same version, so a rule change never applies halfway through a session. **Pattern:** Strategy with a versioned registry. Each version is a `Ruleset` (a struct of rule functions); a change adds a new function only for the rule that changed and a new version that reuses the rest; services call `rules.For(session.RulesVersion)`, never a rule directly. The one `.wasm` build carries every live version and the device picks the session's. Cases live per version (`cases/v<n>/…`) and the tests run every live version. **Live versions:** a version is removed once no open or unsynced session uses it; normally two are live (current and previous). **Bumping:** any change to what a shared rule returns bumps the version; a refactor with identical results doesn't, and the cases prove it. **Urgent fixes:** a version with a real bug (for example one that allows a double booking) is marked `retired`; the server then rejects it, and the device loads the latest build and moves the session to the current version at its next sync, with a notice to the Queue Master. Retiring is the owner's call and should be rare.
