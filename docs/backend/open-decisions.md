| B-48 | **The live-update publisher reads in transaction order, so it never skips a write.** *Amended November 15, 2026: the first version moved the cursor by event id, which still skips a write whose transaction id is older but whose event id is lower than one already pushed (a write that changes or locks a row early, then inserts its event late).* Event ids are handed out at insert, not at commit, so they can't be the cursor. Each event stores its writing transaction's id (`xact_id`, type `xid8`, database default `pg_current_xact_id()`). The publisher reads events with `(xact_id, id) > cursor` **and** `xact_id < pg_snapshot_xmin(pg_current_snapshot())`, ordered by `xact_id, id`; the cursor is the `(xact_id, id)` of the last event read. Every transaction below that limit has finished and every later one gets a higher transaction id, so nothing can appear behind the cursor. **Stream position:** the SSE event id and the phone's `Last-Event-ID` carry the same position as a short string (`"<xact_id>:<id>"`); the catch-up uses the same rule. The live message still carries the session's new **event id** as its snapshot version (B-25, B-49). A ping waits at most as long as the slowest write still running (normally milliseconds); read-only transactions (backups, reports) get no transaction id and never hold it back. **Guard:** `idle_in_transaction_session_timeout` on the API's database role (a few seconds) and a publisher-lag panel in Grafana (B-16), since a write left open delays every ping. Needs Postgres 13 or later (check Railway and Supabase). Tested with this exact shape: write R takes its transaction id first and inserts its event last, write E inserts first and commits last; both reach a connected screen and a reconnect with `Last-Event-ID` gets both.
