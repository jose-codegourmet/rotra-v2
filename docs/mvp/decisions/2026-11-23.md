### D-2026-11-23-01 — Player lookup finds unclaimed players by name and shows their name and picture
- **Decision status:** approved (owner, November 23, 2026): "unclaimed players should be searchable!", then, asked whether to show name and photo, search by name, or both: "Both".
- **Implementation status:** implemented (mockup, mock app and real services) in [#1030](https://github.com/jose-codegourmet/rotra-v2/pull/1030).
- **Ticket:** none (owner request in the session).
- **Roadmap:** MVP — [Queue](../workstreams/queue.md)
- **Decision:**
  - **Name search for unclaimed players.** Add player › Player Information (in a session and in Saved players) also finds **unclaimed** players by part of their name (two letters or more, any club's name for them). Registered players are still found only by exact RTR ID or email ([D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04)); a guest is never found.
  - **Name and picture shown.** An unclaimed player another club saved shows a name and picture: the version of the club that saved them first (its current record), in place of "Not registered yet".
  - **This club still keeps its own name.** Picking them asks for this club's name for them, prefilled with the name shown; each club keeps its own version as before.
- **Supersedes:** part of [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04) ("no name search there"; "no club is shown another club's name, picture or level" for Player lookup results). Levels stay club-only.
- **References:** [mockup log](../../mockup-changes/2026-11-23-queue-unclaimed-name-search.md).

### D-2026-11-23-02 — A social link is an entry key for an unclaimed player
- **Decision status:** approved (owner, November 22, 2026, in [#1019](https://github.com/jose-codegourmet/rotra-v2/issues/1019)).
- **Implementation status:** implemented (mockup, mock app, real services) in [#1023](https://github.com/jose-codegourmet/rotra-v2/pull/1023), [#1026](https://github.com/jose-codegourmet/rotra-v2/pull/1026). Migration `20261123000100_shared_entry_social_key` applied to the shared database 2026-11-23.
- **Ticket:** [#1019](https://github.com/jose-codegourmet/rotra-v2/issues/1019)
- **Roadmap:** MVP — [Queue](../workstreams/queue.md), [Player](../workstreams/player.md)
- **Decision:**
  - A name plus a Facebook, Instagram, YouTube or LinkedIn link saves an **Unclaimed** player with an RTR ID, like an email. With neither an email nor a link, the player is a Guest.
  - One normalized link is one unclaimed person across clubs (`m.`/`www.`/`mobile.`/`fb.com` become the provider's site; no query, hash or trailing slash; lower case). A second club entering it gets the same person and RTR ID.
  - The key only matters while the person is unclaimed. Registering through the club's invite link makes them own that RTR ID at once; from then on the link is an ordinary profile link, never used to find or match them. Claiming is by invite link only.
  - If the email and the link point to two different unclaimed players, the link wins.
  - The club can edit and remove the link; the link is public on the profile card; with no email and no link left, the club's record goes back to Guest.
  - Player lookup also finds an unclaimed player by exact link. Offline, an entry with a link waits as Lookup pending.
  - A player saved with a link only reads "Saved by your club with a social link" on their profile and invite.
- **Supersedes:** part of [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04) (an unclaimed player needed an email).
- **References:** [mockup log](../../mockup-changes/2026-11-23-queue-social-link-entry-key.md), [wording log](../../mockup-changes/2026-11-23-queue-link-only-player-wording.md).

### D-2026-11-23-03 — Add player › New player takes a phone and a profile picture, with the same fields in both contexts
- **Decision status:** approved (owner, November 23, 2026): "can we be able to also input the phone number and avatar"; "add player in session and add player in club … they both should have the same fields".
- **Implementation status:** implemented (mockup, mock app, real services) in [#1027](https://github.com/jose-codegourmet/rotra-v2/pull/1027), [#1031](https://github.com/jose-codegourmet/rotra-v2/pull/1031). No migration (uses `club_players.avatar_ref` from [D-2026-11-09-12](2026-11-09.md#d-2026-11-09-12) and the existing club phone intake).
- **Ticket:** none (owner request in the session).
- **Roadmap:** MVP — [Queue](../workstreams/queue.md)
- **Decision:**
  - **Phone (optional)**, private to the club, kept for an unclaimed player only: refused with no email and no social link (a guest has no phone), and refused when another saved player already has the number.
  - **Profile picture (optional)** on New player in both Saved players › Add player and the session Add player. In a session the picture is saved once the roster change has synced; if it can't be, the player stays added and the club sets it in Edit details.
  - Both Add player contexts have the same New player fields; only the tabs differ (a session also has Saved players).
- **Supersedes:** part of [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04) ("No phone is asked" on New player).
- **References:** [phone and picture log](../../mockup-changes/2026-11-23-queue-new-player-phone-picture.md), [session parity log](../../mockup-changes/2026-11-23-queue-session-new-player-picture.md).

### D-2026-11-23-04 — The club gives a saved player a level outside a session
- **Decision status:** approved (owner, November 23, 2026): "the club owner should be able to give them skill level … if they can add skill level during adding a player they should be able to edit it also".
- **Implementation status:** implemented (mockup, mock app, real services) in [#1028](https://github.com/jose-codegourmet/rotra-v2/pull/1028). Migration `20261123000300_club_player_saved_level` applied to the shared database 2026-11-23.
- **Ticket:** none (owner request in the session).
- **Roadmap:** MVP — [Queue](../workstreams/queue.md)
- **Decision:**
  - The **Level for this club** chosen in Saved players › Add player (New player or Player Information) or in **Edit details** is the saved player's level (`club_players.saved_skill_level_id`, `saved_level_at`).
  - Saved players show it, or the latest session level when that is newer; sessions still set their own level.
  - Guests and unclaimed players only (registered players have no Edit details). A level can be changed, not cleared.
- **References:** [mockup log](../../mockup-changes/2026-11-23-queue-saved-player-level.md).

### D-2026-11-23-05 — Unclaimed players saved by clubs have a public profile in the Player app
- **Decision status:** approved (owner, November 23, 2026): "unclaimed players should be searchable in player app".
- **Implementation status:** implemented (real services) in [#1032](https://github.com/jose-codegourmet/rotra-v2/pull/1032); the Player prototype already behaved this way. No migration.
- **Ticket:** none (owner request in the session).
- **Roadmap:** MVP — [Player](../workstreams/player.md)
- **Decision:**
  - The Player app's RTR ID lookup (`/find/RTR-…`) finds an unclaimed player a club saved (a shared entry) and opens their profile.
  - The profile shows the name, nickname, picture, playing style, experience and links of the club that saved them first, their RTR ID and "saved by" that club, their games and clubs. No rank and no leaderboard place.
  - It is public while exactly one club has saved them, and for signed-in players only with more ([D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04), unchanged).
  - Their registration link's **Is this you?** card shows the picture the club set ([#1029](https://github.com/jose-codegourmet/rotra-v2/pull/1029)).
