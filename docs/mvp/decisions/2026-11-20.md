### D-2026-11-20-01 — Google sign-in in real mode: the Admin link, the inviter on a session invite, one accepted risk
- **Decision status:** approved (owner answers on #922, November 20, 2026).
- **Implementation status:** in progress — written in #922 behind the flag `player_google_sign_in` (off), not run against Google or a database. Migration `20261120000100_admin_link_registration` is applied to the shared database 2026-11-22 (owner request). [Setup and design](../../backend/google-sign-in-setup.md).
- **Ticket:** [#922](https://github.com/jose-codegourmet/rotra-v2/issues/922) (Epic P12, #892)
- **Roadmap:** MVP — [Player](../workstreams/player.md)
- **Decision:**
  - **Migration `20261118000200_player_google_sign_in` is applied to the shared database.** Google itself is not set up yet (#896), so nothing has run against Google.
  - **Registration from the Admin link is built completely in real mode, no gaps.** As the identity rules say ([D-2026-11-09-06](2026-11-09.md#d-2026-11-09-06)): the Admin link gives no club and asks for a city or province for the player ID. The RTR ID (`RTR-PH-<CITY>-<MMDDYY>-<seq>`) takes its place from the city the player picks, one of the Admin-managed founding cities; an email clubs already saved keeps its RTR ID and needs no city ([D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04)). The player is added to no club. This covers Google registration and, with the flag off, the email + password registration from the same link, which was not built in real mode either.
  - **A session invite names the inviting player in real mode.** The invite card (P-INVITE) and the signed-in join step (P-JOIN-SESSION) read the link's Session invite code: the card names the player who made it, that player sees their own invite, and an unknown code shows no inviter. The codes were already stored (`session_invite_codes`, migration `20261118000700_drop_out_notices_session_invites`, applied to the shared database on November 19, 2026), so no new table was needed; the code is the only thing in the link.
  - **Accepted risk:** an unconfirmed password account registered with someone else's Gmail address is offered **Connect Google to your account?** when the Gmail's real owner signs in with Google, and a yes signs that person in to it. The owner keeps this as built: it would affect few of the ~80+ players registered before November 20, 2026. Not an open item any more.
  - **By design, not a gap:** connecting Google to an already-registered profile at claim. A registration link for a registered profile shows "already registered" and **Sign in**, and a person who already has an account cannot attach a record through a link ([D-2026-11-18-07](2026-11-18.md#d-2026-11-18-07)); they connect Google from Sign-in methods after signing in.
- **Before this code is deployed and before the flag is turned on:** apply `20261120000100_admin_link_registration` (it lets an RTR ID and a registration's staging link have no club). Until then an Admin-link registration in real mode (password or Google) fails with an error and saves nothing.
- **Not in this decision:** the Queue Master seeing "Invited by <name>" on a join request (`session_join_requests.invite_code_id` is still not set by the Queue join).
- **References:** [identity module](../../business_logic/product/player-information/modules/identity/README.md#login-and-recovery), [identity design](../../database_design/product/player-information/modules/identity.md#rtr-id-allocation), [physical schema › P12.7](../../database_design/product/physical-schema.md), [sessions and roster design › `session_invite_codes`](../../database_design/product/queue/modules/sessions-roster.md#session_invite_codes), [D-2026-11-16-01](2026-11-16.md#d-2026-11-16-01), code `packages/db/src/player/{guest-registration,identity,invite-landing}.ts`, `apps/player/src/app/api/register/{route.ts,google/route.ts}`.

### D-2026-11-20-02 — Record games off: games are recorded as usual, but their wins don't count toward the leaderboards or win rate
- **Decision status:** approved (owner, November 20, 2026: “when games are not recorded they are still gonna have leaderboards, the games will still be recorded but the wins will not be counted for the ranking”; then, the same day: “the only difference is those wins wont be part of the recorded wins for leaderboard, it wont affect the winrate”; and keep the name “Record games”; answers the same day: leave them out of the skill rank, and don't count them toward the Provisional or leaderboard game counts; write the migration and test it locally only). The open items below are not decided.
- **Implementation status:** Queue built (November 24, 2026). Match done takes the winner and score (November 22). Mock app and UI: #1079 (Not ranked chip and notice, results and the public page as usual, four finishing steps, the “… not ranked” toast). Real mode: #1080 — Session done writes facts, summaries, the result snapshot and the history job as for any session (no rank job); the Top annual / monthly / weekly leaderboards, the rank evidence counts, win rates and Compare skip the session by `queue_sessions.record_games`; a player's match history marks its games `not_ranked`. Still mockup only: the Player app's “Fun, partial and not ranked” list, chip and note ([Player log](../../mockup-changes/2026-11-20-player-not-ranked-games.md), #1090). Database: migration `20261120000200_record_games_ranks_only` (applied to local disposable databases; recorded as applied in the shared database's migration history, seen 2026-11-24).
- **Ticket:** #1079 (mock app and UI), #1080 (real mode), #1090 (Player app).
- **Roadmap:** MVP — [Queue](../workstreams/queue.md), [Player](../workstreams/player.md)
- **Replaces:** the “Off means run only, keep nothing” line of [D-2026-11-18-06](2026-11-18.md#d-2026-11-18-06). The switch itself (session form, on by default, fixed after Start) is unchanged.
- **Decision:**
  - With **Record games** off, the session runs and records exactly like a recorded one: Match done takes a winner and score; the Leaderboard, Match History, standings, result slides, awards and Publish results all work; finishing updates player records; the games appear in each player's history in the Player app with the night's win or loss.
  - **The only difference:** those wins and losses are not part of the **Top annual / monthly / weekly** leaderboards' wins and do not affect the player's **win rate**. The Player app lists them with fun and partial games (“Fun, partial and not ranked”) with a **Not ranked** note.
  - They also don't move the shared skill rank, and they don't count toward the Provisional game count or the leaderboard game count (owner's answers: like fun games).
  - The switch keeps the name **Record games**; Off reads “Off · not ranked”, and the session shows a **Not ranked** chip.
- **Open:**
  - Whether a not-ranked session counts for “has played at this club before” and the award baselines (Most Improved / Off Day) (mockup: no change shown).
  - Database: migration `20261120000200_record_games_ranks_only` (written; applied to a local disposable database 2026-11-20; recorded as applied in the shared database's migration history, seen 2026-11-24) makes every completed decision need a winner again. The services are built (#1080): finishing writes `player_match_facts` for these sessions, and the leaderboard, win-rate and rank reads skip facts from a session with `record_games = false`.
