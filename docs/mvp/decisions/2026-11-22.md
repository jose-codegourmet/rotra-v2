### D-2026-11-22-01 — Trusted club hosts and session host display
- **Decision status:** approved (owner, epic [#1002](https://github.com/jose-codegourmet/rotra-v2/issues/1002), November 22, 2026).
- **Implementation status:** implemented (mock app + real services) — #1003 (Club settings › Trusted hosts), #1004 (session setup › Hosts with auto-registration), #1005 (change hosts before and during the session), #1006 (public Hosts section), #1007 (Host badge on the profile Clubs card) and #1008 (finished sessions keep their hosts) are in the mockup, the mock app and real mode (services + Route Handlers). Migrations `20261122000100_club_trusted_hosts`, `20261122000200_session_hosts` and `20261122000300_session_host_snapshots` are written and checked on a local disposable database only, **not applied to the shared database** (owner sign-off needed).
- **Ticket:** [#1003](https://github.com/jose-codegourmet/rotra-v2/issues/1003), [#1004](https://github.com/jose-codegourmet/rotra-v2/issues/1004), [#1005](https://github.com/jose-codegourmet/rotra-v2/issues/1005), [#1006](https://github.com/jose-codegourmet/rotra-v2/issues/1006), [#1007](https://github.com/jose-codegourmet/rotra-v2/issues/1007), [#1008](https://github.com/jose-codegourmet/rotra-v2/issues/1008) (epic #1002).
- **Roadmap:** MVP — [Queue](../workstreams/queue.md), [Player](../workstreams/player.md)
- **Decision:**
  - **Hosting is informational, not authorization.** The club account (club credentials) stays the only way to operate the Queue app. No new roles, permissions or logins.
  - **Trusted hosts.** The club keeps a **trusted-host list** drawn from its saved players, in **Club settings › Trusted hosts**: add from saved players not on it, remove with a confirmation. Saved players can be trusted hosts without a ROTRA account (guests and unclaimed players). The list is separate from saved-player membership and from Queue permissions: adding or removing changes only the list.
  - **Removing a trusted host** removes their current Host badge and their place first in the host picker, but never their saved-player membership nor historical session host records. Past sessions keep host snapshots.
  - **Session hosts.** A Queue Session's **Hosts** section is optional (zero hosts is valid). Session creation can select several trusted hosts. Assigning a host auto-registers that person as a playing participant (roster), using one capacity slot (two hosts = 2/16), without duplicating an existing registration; capacity follows the existing roster and waitlist rules when full.
  - **Another saved player as host.** The session creator may pick a non-trusted saved player as host with a plus picker; a confirmation says this permanently adds them to the club's trusted-host list. Already selected hosts can't be picked twice. Picker order: trusted hosts first, then other saved players.
  - **During a session** hosts can be changed. Removing a host designation never removes their player registration; withdrawing as a player never removes the host designation. The existing queue controls handle withdrawal, rejoin and the waitlist.
  - **Host badge.** When a trusted host is linked to a ROTRA player account, their public player profile's Clubs section shows a **Host** badge for each club where they are currently trusted.
  - **Public queue page:** a compact **Hosts** section, then Players, then Waitlisted. A host who plays appears in both Hosts and Players but counts once toward capacity.
  - **Words:** *Trusted host* (code `trustedHost`) and *Host* (code `sessionHost`) in [product terms](../../product-terms.md#4-players-identity-and-presence). UI copy: "Trusted hosts" (Club settings), "Hosts" (session setup, management and public page), badge "Host".
- **Data model (agreed shape):**
  - `club_trusted_hosts` (#1003, Prisma `ClubTrustedHost` in `schema/queue/club-host.prisma`): `id`, `club_id`, `club_player_id` (scoped FK to `club_players`, RESTRICT), `added_at`, `removed_at` (null = current; soft, so history stays), `created_at` / `updated_at` / `revision`. One current row per `(club_id, club_player_id)` (partial unique index where `removed_at` is null). RLS on, no anon/authenticated grants.
  - `session_hosts` (#1004, same file): `id`, `club_id`, `session_id` (FK to `queue_sessions`), `club_player_id` (FK, RESTRICT), `assigned_at`, `removed_at` (null = current host), timestamps. One current row per `(session_id, club_player_id)`.
  - Snapshot columns on `session_hosts` (#1008, migration `20261122000300_session_host_snapshots`): `name_snapshot` (text, required: the host's name at assignment, the ROTRA full name for a linked record, else the saved player's name) and `frozen_at` (set when the session ended on the rows current then), so finished sessions show their hosts after a trusted-host removal, a saved-player removal or identity linking (`linked_to_club_player_id`). No `player_id` snapshot: the row keeps its `club_player_id` (RESTRICT), which already reaches the record and its picture.
  - Mock mode: the mock store keeps `clubTrustedHosts` (current and removed rows); the trusted-host hooks are `useTrustedHosts`, `useAddTrustedHost`, `useRemoveTrustedHost` (`@rotra/data/trusted-host/*`).
- **Settled in #1003:** a trusted host whose saved player the club deleted, or moved into another saved player (Same person), drops off the list read; the row stays as history. Toasts: "NAME added to trusted hosts", "NAME removed from trusted hosts". Club settings stays online only.
- **Settled in #1004 (session setup › Hosts):**
  - The Hosts field sits on setup page 1 › Courts, under the slot budget, with a **Hosts** row in the review. The setup payload carries `hostClubPlayerIds` (the full list after the save; left out = unchanged); every date of a repeating series gets the same hosts.
  - The trusted-host confirmation adds the saved player to the trusted-host list **at confirm time** (not at save), so it stays even if the setup is abandoned, as the copy says (“permanently adds”). A save refuses a new host who is not a current trusted host; hosts already on the session stay even if later removed from the list.
  - **Capacity:** there is no host-specific rule, so the existing preparation rule applies: new hosts take open slots in the order picked, and the rest go on the end of the waitlist (never past the budget; Add anyway stays a Queue Master choice in Add player). The setup warns before saving. Already registered (slot or waitlist, or another saved record of the same ROTRA player in the mock) = no new registration.
  - A host is registered with their saved level (mock: the saved player's level; real: the latest club assessment) or, without one, with no level (set in Roster and levels before Start; a waitlisted host without a level is skipped by automatic fills, as today).
  - Removing a host in Edit preparation ends only the host row. Deleting a prepared session deletes its host rows.
  - Toasts: the save adds “· N hosts registered” / “· N hosts waitlisted”; the confirmation toasts “NAME added to trusted hosts”.

- **Settled in #1008 (finished sessions keep their hosts):**

A host removed before the end (`removed_at` set) is never frozen and is **not** a host of the finished session; the row stays as history. A cancelled session (never started) is not frozen and keeps its current rows.
  - **Reads:** an open session (prepared, active) reads its current rows (`removed_at` null), as before; a completed or invalid session reads its frozen rows (`frozen_at` set), named by `name_snapshot`. That covers the public page (masked for visitors exactly as in #1006, through `maskPublicName` / `publicPerson`), the Player app's signed-in access read, `GET /api/sessions/[sessionId]/hosts` (now with `name`) and the session record. Hosts show after the club removes the trusted host, deletes the saved player (`club_players.removed_at`) or moves the record into another (Same person, `linked_to_club_player_id`).
  - **Database guard:** a check keeps a frozen row current (`frozen_at` only with `removed_at` null), `name_snapshot` must not be blank, and the trigger `session_hosts_frozen_guard` refuses to change or delete a frozen row and refuses `frozen_at` on a session that has not ended (completed or invalid). The backfill names existing rows from the saved player and freezes the current rows of already completed or invalid sessions at `finalized_at` (else `updated_at`).
  - **Same person during a session:** a current host row of a prepared or active session moves to the surviving record with that record's name (or ends, when the surviving record already hosts that session), like the live slot. Finished sessions keep their frozen rows on the moved record.
  - **Picker:** the trusted-host part of the host picker reads the current trusted-host list (`removed_at` null, saved player current), so a removed trusted host is listed only with the other saved players (#1004/#1005 already did this; checked, no change).

Removing a trusted host or a saved player later doesn't change them.” The Player app has no session details screen that lists hosts, so nothing changed there.

Demo: Sunday Night Queue (`h2`, a week ago) was hosted by Aaron (taken off the trusted-host list two days ago) and still shows him; Gab Torres was its host until an hour in and is not shown.

### D-2026-11-22-03 — Slot transfer: the player requests, the Queue Master approves or rejects, before Start only
- **Decision status:** approved (epic [#1009](https://github.com/jose-codegourmet/rotra-v2/issues/1009) confirmed decisions; owner answers on #1015, November 22, 2026).
- **Implementation status:** built in the mock app and in real mode: the signed-in Player's **Transfer my slot** on My night (Player app routes `POST /api/public-sessions/[slug]/slot-transfer`, `…/lookup`, `…/withdraw`) and the Queue Master's **Slot transfers · N** in Requests (`POST /api/sessions/[sessionId]/requests/transfers/[transferId]/approve` and `…/reject`; the Requests read carries `transfers`). Migration `20261122000400_session_slot_transfers` applied to a local disposable database only; **not applied to the shared database: owner sign-off needed.** Mockup: [log](../../mockup-changes/2026-11-22-queue-slot-transfer.md).
- **Ticket:** [#1011](https://github.com/jose-codegourmet/rotra-v2/issues/1011) (epic [#1009](https://github.com/jose-codegourmet/rotra-v2/issues/1009))
- **Roadmap:** MVP — [Queue](../workstreams/queue.md)
- **Decision:**
  - A signed-in Player **confirmed** in a session asks to transfer their slot to another **registered** ROTRA player, picked by **exact RTR ID** (the same exact-match rule as Player lookup, [D-2026-11-16-04](2026-11-16.md#d-2026-11-16-04); never a name, a guest or an unclaimed person). One pending transfer per slot.
  - The Queue Master, signed in with the club account, **approves** (with the level the recipient plays at here, like confirming a join request) or **rejects** it in Requests, beside the drop-out notices.
  - **Before the session starts only.** Start expires every pending transfer (`expired`); Cancel session cancels them (`cancelled`). The sender may **withdraw** a pending one (`withdrawn`). A decided transfer is final (immutable).
  - **Approval** swaps the holder in one transaction on the locked session row: the sender's roster entry is released (reason `transferred`), the recipient takes the slot in the sender's place in slot order. The slot count never changes and the recipient ends with exactly one entry. A **waitlisted** recipient is promoted out of the waitlist; an **already-confirmed** recipient is refused at request and checked again at approval. The recipient's own pending join request and the sender's open drop-out notice close.
  - **Rejection** changes nothing else: the sender's registration and payment stay exactly as they were.
  - ROTRA moves no money. The sender's payment mark is not touched by an approval; recipient Paid in Full, the automatic waiver and the chain view are [#1013](https://github.com/jose-codegourmet/rotra-v2/issues/1013).
- **Assumptions made in this ticket (say if wrong):** the sender can withdraw their own pending request (the epic names withdrawal for the recipient's claim, #1012); a player who hid themselves from Player Information cannot be found by RTR ID here either; the status word is spelled `cancelled` like every other status in the code.
- **Shape kept ready, not built:** transfer links (#1012), waiver and payment snapshot with the chain of custody (#1013), refunds (#1014), leaving a club cancels pending transfers (#1018). See the [database design](../../database_design/product/queue/modules/sessions-roster.md#session_slot_transfers).
- **References:** [players module › Slot transfers](../../business_logic/product/queue/modules/players/README.md#slot-transfers-1011), [public session screen](../../screens/product/modules/queue/public-session.md), [session setup › Requests](../../screens/product/modules/queue/session-setup.md), code `packages/data/src/slot-transfer`, `packages/db/src/queue/slot-transfers.ts`.

### D-2026-11-22-04 — Transfer links: a single-claim link for a recipient with no ROTRA account, first signed-in claimant, invalidation
- **Decision status:** approved (epic [#1009](https://github.com/jose-codegourmet/rotra-v2/issues/1009) confirmed decisions; owner answers on #1015, November 22, 2026).
- **Implementation status:** built in the mock app and in real mode: **Create a transfer link** on the Transfer my slot sheet, the **Transfer link** sheet (QR, copy, share), **Cancel link** on My night, the transfer link card on `/s/<slug>?transfer=<token>` (Player app routes `POST /api/public-sessions/[slug]/slot-transfer/link`, `…/link/read`, `…/link/claim`, `…/link/withdraw`), and “Claimed by NAME” in Requests. Migration `20261122000500_slot_transfer_links` applied to a local disposable database only; **not applied to the shared database: owner sign-off needed.** Mockup: [log](../../mockup-changes/2026-11-22-queue-transfer-links.md).
- **Ticket:** [#1012](https://github.com/jose-codegourmet/rotra-v2/issues/1012) (epic [#1009](https://github.com/jose-codegourmet/rotra-v2/issues/1009))
- **Roadmap:** MVP — [Queue](../workstreams/queue.md)
- **Decision:**
  - When the recipient has no ROTRA account, the confirmed sender makes a **transfer link** instead of picking an RTR ID, and shares it. One pending transfer per slot, link or RTR ID ([D-2026-11-22-03](#d-2026-11-22-03)).
  - The link is the transfer row itself: a pending transfer with no recipient. It **works exactly while that transfer is pending and the session is Prepared**. So Queue Master **rejection**, **withdrawal** by either side, **Start** (`expired`) and **Cancel session** (`cancelled`) all end it, and the sender makes a new link to try again.
  - The claimant must **sign up or log in**. Signing up goes through the session link's registration (`/register/<clubId>?session=<slug>`), so identity and the RTR ID work exactly like a session link. Club membership on signing up is [#1018](https://github.com/jose-codegourmet/rotra-v2/issues/1018); the claim service marks where it hooks in.
  - The **first signed-in acceptance** claims the link (one claimant per link). It is one conditional update on the locked session and transfer rows (`recipient_player_id IS NULL`), and a trigger refuses any later change of the recipient or the token. A second claimant sees “Someone else already claimed this transfer link.”
  - A claimed link then waits for the Queue Master exactly like a request by RTR ID: Approve with a level, or Reject. The sender and anyone already confirmed in the session cannot claim. A waitlisted claimant can, and the approval promotes them.
  - The claimant may **withdraw** their pending claim; the link stops working.
  - Only a **SHA-256 digest** of the opaque token (32 random bytes, base64url) is stored, like the registration claim links. The token is shown once, when the link is made.
  - The sender's name on the link card is masked like every name on the public page. ROTRA moves no money.
- **Assumptions made in this ticket (say if wrong):** a lost link cannot be shown again (only its digest is kept), so the sender cancels it and makes a new one; the sender can also cancel a link that someone already claimed, like withdrawing a request; the claimant acts on the link's own page (My night only covers people on the roster or waitlist).
- **References:** [players module › Transfer links](../../business_logic/product/queue/modules/players/README.md#transfer-links-1012), [public session screen](../../screens/product/modules/queue/public-session.md), [database design](../../database_design/product/queue/modules/sessions-roster.md#session_slot_transfers), code `packages/data/src/slot-transfer`, `packages/db/src/queue/slot-transfers.ts`, `packages/ui/src/components/transfer-link-card`, `packages/ui/src/components/transfer-link-sheet`.
