# Existing command and read contracts

**Last verified:** 2026-10-28 · **Code baseline:** `7d7029d` on main.
**Ticket:** [#242](https://github.com/jose-codegourmet/rotra-v2/issues/242), under [F07](https://github.com/jose-codegourmet/rotra-v2/issues/241).

This inventory freezes the **observed mock interface for planning**, not a production API or an assertion that the flows run. It covers the 21 domain directories in `packages/data/src`, their query/mutation hooks, and documented actions without a current fetcher. The [callable catalog](callable-catalog.md) records exact inputs, output summaries and hook links; the tables here supply actors, lifecycle, errors, retries and cache effects. Read both before replacing a fetcher. Recheck the current branch when implementing: other feature tickets remain active.

## Shared boundary

- A **club** acts only for its own club under the documented entitlement, including the narrow active-session finish/sync exception. A **player** acts for their own account. **Public** reads use allowlisted projections. **Owner** means the platform owner, not an operator using club credentials. These are required product authorities, not claims that the mock enforces them.
- Current errors are [`MockError`](../../../packages/data/src/mock/errors.ts): `retryable`, `permission`, `conflict`, `offline`, with optional field errors. Validation also includes Zod errors; cancelled requests may abort. Do not blindly convert every existing `permission` into HTTP 403: mocks also use it for validation/not-found. Error/status serialization belongs to [#243](https://github.com/jose-codegourmet/rotra-v2/issues/243) / [#261](https://github.com/jose-codegourmet/rotra-v2/issues/261).
- [`queueMutation`](../../../packages/data/src/mock/transaction.ts) produces `SaveOutcome & { data }`, where `SaveOutcome` is `{ savedOffline, message }`. It makes an in-memory update and sync-log entry together; that is **not durable offline persistence**. Session writes generally require prepared/active state and a ready download when simulated offline. Individual commands add stricter guards or deliberately use a different lifecycle.
- Only callers that supply an operation ID and payload fingerprint get `queueMutation` replay protection. The match control functions do; most preparation, queue, settings and payment commands do not. Finalization has a separate `commandId`. There is no general expected-revision parameter in the mock interface. Server revision/operation envelopes must be reviewed before real transport, not silently inferred from repeated button clicks.
- Default reads are repeatable queries, not proof of a server snapshot. A cached offline read does not authorize a write. Player queries use [`playerRequest`](../../../packages/data/src/leaderboard/request.ts); most Queue reads simply return in-memory state. Individual gates below distinguish those simulations from the target.
- [`useMockMutation`](../../../packages/data/src/mock/query.ts) invalidates **every non-auth query** on success. Preserve all affected consumers when narrowing this later. Other hooks explicitly invalidate/set/remove keys; the catalog links their actual implementations and query-key definitions. No Redux copy becomes canonical data.

**Read-specific handling:** session record/history require completed/invalid state; result/publication reads may be null before output exists; invalid payments return null; own account/request return null when signed out. Public missing slug uses `PublicSessionNotFoundError`; missing player/rank/history behavior is defined by each linked return type. License payments require online; club access can be unverified. Player/leaderboard/profile/account reads using `playerRequest` require online and support cancellation. Do not turn these distinct empty/not-found/permission states into one fabricated successful DTO.

## Transport review handoff

No application `route.ts` files exist at this baseline. The hook surface above is not a list of approved HTTP URLs. In #243/#261, review concrete route names **separately**, grouped by the existing actor/domain actions, against [navigation](../../screens/product/navigation.md) and Next.js Route Handler conventions. Public visitor, Player owner and Club/Owner commands require distinct authorization even if they share a table. Resolve actor from a verified session, never a caller-supplied `clubId` or demo cookie.

Before each integration PR, specify the exact URL/method, input/output serialization, expected revision, stable operation/receipt identity, error mapping, offline permission and invalidated query families. A migration-safe schema does not by itself supply any of those contracts. No Server Actions, Realtime, new routes or new dependencies are approved by this inventory.
